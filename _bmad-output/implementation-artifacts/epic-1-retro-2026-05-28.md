# Epic 1 Retrospective: 企业组织与部门治理基线

日期：2026-05-28

## Epic Review

Epic 1 已完成 4/4 个 story：

- Story 1.1 查看企业部门树：新增企业部门模型、迁移、树查询 API、Default/Classic 管理入口和基础测试。
- Story 1.2 维护用户与部门 N:N 成员关系：新增成员关系模型、生命周期服务、成员维护 API、未归属语义和测试覆盖。
- Story 1.3 保持部门权限与 Group 语义分离：新增部门角色/权限服务和中间件，确认 `User.Group`、`Token.Group`、渠道分组、模型倍率与 relay DTO 不受部门能力影响。

## What Went Well

- 企业模块边界基本成立：后端落在 `model/enterprise`、`service/enterprise`、`controller/enterprise`、`dto/enterprise`、`router/enterprise-router.go`，避免把组织能力塞进既有 Group、relay 或 billing 主链路。
- Story 1.3 的权限服务把“系统管理员/Root 全局能力”和“部门管理员局部能力”分开，降低了后续预算、用量、风险模块误用前端可见性的风险。
- Story 1.4 把成员变更和部门权限变更的审计写入事务路径，后续 Epic 3 的配额分配也可以继续遵守“预算审计单一来源”的边界。
- 针对 `relay/**`、`pkg/billingexpr/**`、`model/log.go`、`controller/log.go`、`router/relay-router.go`、`docs/openapi/relay.json` 的边界扫描在 review 中发挥了作用，及时清理了不属于 Epic 1 的漂移。

## Challenges

- 早期 story 曾携带回归门补丁导致范围漂移，review 需要额外做 scope cleanup。后续 story 应把“验证所需修复”和“story 交付范围”拆得更清楚。
- Story 1.2 暴露出 inactive membership 默认查询语义问题。这个问题提醒后续同步、预算和用量 story 必须显式区分“历史关系”和“当前有效关系”。
- Default 前端、Classic 前端、OpenAPI、后端 service/controller/test 同时变化，容易遗漏 File List 或 i18n 同步。后续 enterprise story 需要把这些检查作为固定完成项。
- 主工作区存在与 story worktree 无关的脏文件。后续继续使用独立 worktree 是正确策略，但收尾时要明确只在目标 story branch 上操作。

## Key Learnings

1. 部门关系必须一直按 N:N 当前有效成员关系建模，不允许通过主部门、唯一部门或 `Group` 字段偷懒。
2. 企业权限必须以后端服务为准，前端导航和按钮可见性只能作为用户体验辅助。
3. 企业审计要区分管理动作审计与预算分配审计。Epic 1 的 `enterprise_admin_actions` 不应承担 Epic 3 的配额分配单一审计来源。
4. 范围边界测试很有价值。对 forbidden path 的实际 git diff 扫描比只扫 imports 更能防住 brownfield 改动外溢。

## Next Epic Preparation

Epic 2 是“钉钉企业身份接入与通讯录同步”。它直接依赖 Epic 1 的部门、成员关系、权限和审计基础。

进入 Epic 2 前建议确认：

- 钉钉配置与密钥存储方案只由 Root 管理，API 响应、错误、日志、审计 diff 都不返回明文 secret/token。
- 同步写入部门和成员关系时复用 Epic 1 服务层语义，尤其是停用、恢复、历史追溯和 inactive membership 默认不参与当前归属。
- 钉钉 OAuth 登录只读取最近一次成功同步的本地成员关系快照，不在登录回调路径直接写部门列表。
- 同步任务要有幂等键和状态表设计，无 Redis 时仍可靠；多节点执行需要 `common.IsMasterNode` 或等价守卫。
- Epic 2 的审计策略沿用 Story 1.4：低频配置/同步管理动作进入 `enterprise_admin_actions`，敏感字段必须脱敏。
