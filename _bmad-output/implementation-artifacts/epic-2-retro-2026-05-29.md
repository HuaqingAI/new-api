## What Went Well

- 钉钉能力保持在 enterprise 模块边界内，未侵入 relay、billing expression、核心日志或 relay OpenAPI。
- 密钥与 token 的安全边界延续 Story 1.4 的审计方式：API 响应、前端状态、审计 payload 和测试断言都避免暴露 app secret/access token。
- OAuth 登录路径只读本地成员快照，不在登录回调中写部门关系，降低了高频登录链路污染组织数据的风险。
- 同步任务把“对象级失败”和“可人工处理的冲突”分开：失败进 failed，账号匹配风险进 pending conflict/warning。

## Challenges

- 钉钉身份稳定键、邮箱、手机号三类匹配语义容易互相混淆。Story 2.5 最终采用稳定身份优先，邮箱/手机号冲突只进入 pending，不自动绑定。
- 部门外部 ID 与本地数据库 ID 不一致，测试需要显式按 `external_id` 查本地 ID，避免把上游 ID 当成本地主键。
- `enterprise_dingtalk_identities` 早期没有手机号快照。Story 2.5 通过新增 `mobile` 字段补齐，但老数据需要通过后续 OAuth/同步自然刷新。
- 全量同步的 stale membership 对“离职”和“转部门”只能从本轮是否出现推断。当前用 `left` 状态保守留痕，未来若支持钉钉增量事件可进一步细分。

## Key Learnings

1. 企业身份同步不能用邮箱/手机号做自动绑定的唯一依据；这些字段适合提示候选关系，不适合直接写绑定。
2. 组织历史追溯不一定需要复制整棵部门树，先保存部门名称快照即可满足近期用量追溯需求，并为 Epic 4 聚合展示保留数据。
3. 成员关系状态比删除更适合作为跨 Epic 合同。预算、用量和风险模块都可以基于 active/left/inactive 做自己的策略。
4. 每个 story 独立 worktree/branch 的策略有效，尤其在 Epic 2 这种后端、前端、i18n、测试同时变化的模块里能减少互相污染。

## Next Epic Preparation

Epic 3 是“部门预算池与成员 Wallet 分配”。它会直接依赖 Epic 1 的部门/成员关系，以及 Epic 2 的钉钉同步状态。

进入 Epic 3 前建议确认：

- Budget/wallet 相关审计应建立独立单一来源，不复用 `enterprise_admin_actions` 承担预算流水。
- 分配策略只应读取 active membership；left/inactive membership 的 wallet 回收、冻结或待处理策略必须显式建模。
- 钉钉 pending conflict 的用户不得参与自动预算分配，除非管理员后续完成人工绑定。
- 继续遵守“不触碰 relay 计费链路”的边界，预算分配先建治理层合同，再与实际扣费做后续集成。
