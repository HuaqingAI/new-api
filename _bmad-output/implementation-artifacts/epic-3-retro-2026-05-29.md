## Epic Review

Epic 3 已完成 5/5 个 story：

- Story 3.1 创建部门预算池：落地 `enterprise_department_budgets`、预算池 API、审计和 Default 企业组织页预算入口。
- Story 3.2 将部门预算分配为成员 wallet：把分配真实落地到 `user_subscriptions`，新增 `enterprise_quota_allocations` 审计链，并让企业 wallet 默认排在主钱包前。
- Story 3.3 强制预算铁律与并发安全：补齐 `balance` / `subscription` 两类父池约束，验证 mixed fixed / `tiered_expr` 负载下预算与 wallet 一致性。
- Story 3.4 撤销和联动部门 wallet 状态：新增撤销入口、`wallet_state_sync_task`、`balance_expiry_task` 和 master-node scheduler，保证 paused / revoked / expired 终态联动。
- Story 3.5 展示预算池与 wallet 状态：补齐预算池列表、详情、wallet 明细和企业预算阈值配置。

Sprint 状态显示 Epic 3 的全部 story 均为 `done`，Epic 4 仍为 `backlog`。Epic 3 是当前最高已完成 epic，满足本次 retrospective 的自动确认条件。

## Quality Evidence

Epic 3 的 story 记录中已提供以下关键验证证据：

- Go 回归覆盖 `model/enterprise`、`service/enterprise`、`controller/enterprise`、`tests/api` 的预算池、分配、撤销、状态同步与详情接口。
- Default 前端多次执行 `bun run typecheck`、`bun run test:e2e`、`bun run i18n:sync`，覆盖预算页、系统设置阈值和本地化状态展示。
- Story 3.3 额外执行了 10 分钟、60 worker 的 mixed fixed / `tiered_expr` 长测，确认无父池负余额、无重复回填、无 `allocated_total` 漂移。
- Story 3.4 验证 `wallet_state_sync_task` / `balance_expiry_task` 对 paused 子项同样有效，避免子 wallet 卡在中间状态。

已知限制：

- Epic 4 依赖的部门用量快照、看板与 CSV 还未开始，当前尚未验证预算生命周期与后续用量展示之间的真实运营闭环。

## What Went Well

- 团队守住了最关键的架构边界：Epic 3 没有把部门概念注入 `relay/**`、`pkg/billingexpr/**` 或上游请求 DTO，预算只通过企业 wallet 参与现有订阅扣费链路。
- “企业预算 = 扩展现有 `UserSubscription`” 这个方向在 Story 3.2 被坐实，避免了为企业能力平行再造第二套账本。
- 单一审计源做对了。预算池创建继续用 `enterprise_admin_actions` 记录低频管理操作，而预算分配 / 撤销由 `enterprise_quota_allocations` 独立承接，没有双写漂移。
- Review 驱动改进效果明显。Epic 3 的每个 story 都在 Senior Developer Review 中暴露了高价值问题，并且问题大多能在当前 story 内闭环修正，而不是留给后续故事兜底。
- 前后端集成深度比 Epic 2 更高，但依然保持在 `enterprise` 模块边界内，Default 页面、系统设置、服务层和数据模型之间的契约逐步稳定。

## Challenges

- 架构文档早期使用抽象 `subscriptions` 表述，而仓库真实实现是 `UserSubscription` / `user_subscriptions`。这个抽象落差在 Story 3.1 和 3.2 都造成了实现歧义，必须靠故事 dev notes 和 review 明确收敛。
- 多预算池语义与“按部门取最新一个预算池”的早期实现存在张力。Story 3.5 虽然补齐了列表与详情，但 `GetDepartmentBudget()` 这种旧接口仍带有“latest budget”历史包袱。
- 并发与长测比预期更难。Story 3.3 的真实 10 分钟验证先后暴露了缺少 `subscription_pre_consume_records` 迁移、容量建模不足，以及 SQLite 高并发写锁放大等问题。
- 生命周期联动的坑主要出现在“paused 子项”。Story 3.4 第一次实现里，revoked / expired 父池不会把 paused 子 wallet 推到最终状态，说明状态机设计比单纯 happy path 更容易漏边界。
- 展示层最容易“看起来完成”。Story 3.5 证明，若不强制要求列表、详情、阈值配置和本地化状态同时落地，很容易只做静态卡片而误报 FR12 完成。

## Story Pattern Synthesis

跨 5 个 story 出现的共性模式：

1. 边界保护是 Epic 3 最稳定的成功因素。5/5 个 story 的 dev notes 都反复强调“不碰 relay / billing expression / upstream DTO”，说明团队已经把这条约束内化成实现护栏。
2. 审计与状态模型在 4/5 个 story 中被重新强调。预算池、分配 ledger、wallet 生命周期、详情页展示都依赖“状态字段真实可追踪”，这直接影响 Epic 4 的可观测性基础。
3. Review 发现的问题集中在“代码可以运行，但契约还不稳”这一类：租户透传、预算类型不可变、越权读取、`RowsAffected` 护栏、错误映射、render 期间写状态、paused 子项终态等，说明系统风险正在从“功能缺失”转向“契约精度”。
4. 真正的复杂度不在 CRUD，而在把现有系统接起来。企业 wallet 排序、订阅重置、父池状态联动、系统设置阈值、长测 harness 都是在复用旧链路时出现的复杂性，而不是新表设计本身。

## Key Learnings

1. 对 brownfield 系统做新能力时，最重要的决定不是“新表怎么建”，而是“必须复用哪条旧运行链路”。Epic 3 证明企业预算必须复用 `UserSubscription`，否则后面所有状态、扣费与审计都会分裂。
2. 预算一致性问题不能只靠单元测试证明，必须有长时间、混合计费模型的真实并发验证。Story 3.3 的价值不只是多了一组测试，而是把“不会超配/漏配”从口头承诺变成了可重复运行的证据。
3. 生命周期任务必须从一开始就按状态机思维设计。paused、revoked、expired 这些中间态如果只在 UI 层展示，不在后台任务与服务事务里闭环，最终一定会出现父子状态漂移。
4. 展示层也属于系统契约的一部分。预算阈值如果只写死在前端，详情错误如果把“预算池不存在”映射成“部门不存在”，都会让运维能力失真。

## Significant Discoveries

本次 retrospective 识别出 2 项会影响 Epic 4 启动质量的显著发现：

1. 预算体系已经从“单一预算池卡片”演进为“多预算池 + 详情 + wallet 明细 + 阈值”的真实模型，Epic 4 不能继续假设企业模块是轻量附属页。
   影响：Epic 4 的用量看板、详情和 CSV 需要以预算 / 分配 / wallet 审计链为可解释背景，而不是只从 `logs` 或单个部门视角出发。

2. 企业后台任务现在是实际运行组件，而不仅是架构占位。
   影响：Epic 4 设计聚合和报告任务时，应直接沿用 `common.IsMasterNode` + scheduler + 状态表的模式，而不是重新发明另一套定时任务框架。

结论：Epic 4 方向不需要推翻，但开始前应做一次 story 级准备审视，确保看板/快照/导出故事都建立在 Epic 3 已验证的多预算池与后台任务模型上。
