## What Went Well

- Epic 5 延续了 Epic 4 的“事实源优先”思路。风险分子来自 `enterprise_alert_events`，风险分母复用 `enterprise_usage_snapshots`，没有为风险概览再造第三套统计链路。
- 多部门重复计入与“部门间不可加和”免责声明被真正产品化，而不是只写在 story 注释里。风险事件列表、风险概览、Classic 入口和前端测试都围绕同一口径收敛。
- 告警链路的可追溯性成型了。规则、投递、失败原因、人工重发和 trace payload 形成了可运营、可审计的一整条管理路径。
- review 对 Epic 5 的收益非常高。`5.4` 修正了调度与重试节奏问题，`5.5` 收紧了状态同步，`5.6` 则修复了半开区间边界与多语言/Classic drill-down 漏洞。
- 代码、OpenAPI、Default、Classic 和测试整体保持同步推进，避免了“功能已上线但接口合同或 UI 入口仍然漂移”的老问题继续放大。

## Challenges

- create-story 阶段在 `5.5` 和 `5.6` 都出现了明显空转，说明当前 automator 在某些 story 上容易陷入重复读旧上下文而不产出 artifact。
- Story automator 的 orchestration 状态对 Epic 5 前半段 `5.1`-`5.3` 没有及时同步，导致后续 wrap-up 需要重新按 sprint-status 校正事实源。
- 告警域和用量域的共享口径很容易在边界上漂移，尤其是 `from/to` 时间窗、未归属桶和多部门重复计入。如果没有专门测试，很难在 code review 前肉眼发现。
- Classic 虽然只交付最小入口，但它同样需要守住上下文透传和关键提示文案；否则 Default/Classic 的管理心智会重新分裂。

## Story Pattern Synthesis

跨 6 个 story 出现的共性模式：

1. 真正的复杂度来自共享合同的一致性，而不是单个 API 或单个页面的代码量。事件、规则、投递、重发、风险概览都必须共用同一套 tenant、时间窗、部门归属和 trace 语义。
2. review 的高价值问题主要都属于 contract hardening，而不是“功能完全没做”。Epic 5 后半段的大部分修复都在收敛边界，而不是补大块新代码。
3. enterprise 模块已经形成“后台任务 + 状态表 + 管理 API + Default/Classic 入口 + OpenAPI 合同”的成熟子系统模式，后续 story 继续沿用这一模式会比临时发明新路径更稳。
4. 自动化编排本身也需要被视为产品化对象。source-of-truth 在 sprint-status/story artifact，而不是某个 tmux session 是否还活着，这个经验在 Epic 5 被反复验证。

## Key Learnings

1. 风险类看板不能只靠事件表聚合，必须和已有用量事实源共用同一时间与归因语义。否则“风险率”很快就会变成另一套自洽但不可比较的数字。
2. 多部门重复计入这类业务解释不能交给使用者自己推断，必须在页面、导出、邮件或 API 合同层明确可见。
3. review 不只是在找 bug，也是在纠正统计口径。`created_at == to` 这种边界差异如果不写进测试，业务方几乎不可能从界面上第一时间察觉。
4. 自动编排系统必须信任 source-of-truth 文件，而不是盯着会话活性。Epic 5 证明，只看 tmux monitor 很容易把其实已经完成的 story 错判成“仍在进行中”。

## Significant Discoveries

本次 retrospective 识别出 2 项会影响下一阶段工作的显著发现：

1. `enterprise-alerts` 已经不只是一个事件列表页，而是完整的风险运营台。
   影响：后续若继续扩展风险治理能力，应默认把它当成 enterprise 子系统来设计，而不是零散页面叠加。

2. story automator 在 create-story / retrospective 两类长上下文步骤上比在 dev/review 阶段更容易空转。
   影响：后续继续使用 automator 时，应该把“手动接管 create-story/retro 收尾”视为已有预案，并优先依赖 sprint-status / story artifact 做最终判定。

## Final Summary

Epic 5 把 enterprise 风险治理真正闭成了一条链路：先记录风险事件，再配置规则、投递通知、追踪失败与人工重发，最后回到部门维度看趋势和风险率。相比前几个 epic，这一轮最重要的进步不是单个功能点，而是 shared contract 的稳定度明显提高了。

同时，这次也把自动化编排本身的问题暴露得很清楚。代码交付已经成熟，但 orchestration 状态同步和 retrospective 收尾仍然需要更强的 source-of-truth 机制。这个教训值得在下一轮工作里优先消化。
