## Epic Review

Epic 7 已完成 6/6 个 story：

- Story 7.1 建立部门负责人权限模型与生效优先级：补齐 `manual_deny_override > manual_grant > dingtalk_synced_owner` 的负责人优先级、负责人权限校验和钉钉负责人事实接入。
- Story 7.2 为预算/用量/告警 summary 增加包含子部门作用域：新增 descendant scope resolver，并把预算、用量、告警三个 summary 视图统一到相同的 scope 语义。
- Story 7.3 支持上级预算池向后代部门预算池分配：新增独立 delegation ledger、预算容量约束和后代部门预算委派链路。
- Story 7.4 补齐成员 allocation 的调整、取消与回收治理：把成员 allocation 生命周期扩展到 supersede / cancel / reclaim，并保持审计链条。
- Story 7.5 支持员工额度申请、单步审批与自动分配：新增 quota request 真源、单步审批和审批后自动复用 allocation 链路。
- Story 7.6 建立治理动作审计时间线与钉钉通知：把负责人授权、预算委派、allocation 治理、申请审批与自动分配收敛到统一时间线和非阻塞通知闭环。

Epic 7 的产品目标已经实现：企业板块从“能分配额度”走到了“能治理额度、能审批、能追溯、能通知”的闭环状态。

Sprint 状态显示 Epic 7 的全部 story 已经是 `done`。本次 retrospective 的特殊点在于：原始 automator 子会话因为本地 tmux respawn 故障没有完成 retrospective 收尾，所以这份 retrospective 依据 story artifact、sprint-status、orchestration 日志和定向验证证据手动补做并收口。

## What Went Well

- Epic 7 保持了 enterprise 模块一贯的架构纪律：没有触碰 relay、billing expression 或 AI 协议面，而是通过 enterprise 自己的 model/service/controller/DTO/UI 纵切片完成治理增强。
- 新能力不是平行发明，而是复用既有事实源和服务能力。7.2 复用了部门树解析，7.3 和 7.5 复用了预算池与 allocation 语义，7.6 复用了 webhook 投递边界和通知退避思路。
- “追加事实、保留历史”成为这一轮最稳定的建模模式。预算委派、allocation 调整、额度申请审批都优先采用“关闭旧事实 + 新建新事实”而不是静默覆盖历史。
- Default 前端与后端合同整体保持同步推进。scope toggle、委派入口、allocation 生命周期操作、quota request 审批、governance timeline/notification 都没有落成“后端先有、界面后补”的半成品。
- 定向验证策略是有效的。虽然 automator 的 review / retrospective 会话不稳定，但 story artifact 中保存的验证命令、commit 和变更清单已经足够支撑高置信度收口。

## Challenges

- 当前 automator 最脆弱的不是开发实现，而是长链路状态收尾。create-story、review done、retrospective、wrap-up 都出现了状态不同步或子会话空转。
- Epic 7 暴露了明显的元数据漂移：`sprint-status` 已是 `done`，但 Story 7.3、7.4、7.6 的故事文件仍停在 `review`，orchestration 还留下了“retrospective skipped”的历史状态。这说明 source-of-truth 收口之后缺少自动反写。
- 全量测试信号仍然不够干净。当前团队在 enterprise 模块上的质量门禁更多依赖“定向回归 + 故事证据”，而不是稳定的一键回归入口。
- 未找到 Epic 6 retrospective 文件，导致“上一轮承诺是否被落实”的连续性核账缺失。Epic 7 只能直接从 story artifact 和更早的 retro 中反推流程问题。

## Story Pattern Synthesis

跨 6 个 story 能看到四个清晰模式：

1. 真正的复杂度来自共享治理语义，而不是单个接口。
   负责人优先级、包含子部门 scope、预算铁律、allocation 生命周期、quota request 审批路由、治理 timeline trace ID 都要求前后端共享同一套定义。

2. enterprise 治理能力适合用“事实源 + 投影 + 工作流”思路实现。
   7.3 的 delegation ledger、7.5 的 quota request 真源、7.6 的 governance timeline projection 都验证了这一点。

3. code review 的高价值问题更多是边界和合同加固，而不是“功能完全缺失”。
   7.5 的 senior review 和 7.6 的 JSON wrapper 修正都属于这类收益很高的收敛。

4. 当前流程里最需要被产品化的对象已经不是某个 enterprise 页面，而是 automator 自身的 source-of-truth 同步。
   Epic 7 几乎每个后半程 story 都依赖人工或手动逻辑去做最终状态收口。

## Previous Retro Follow-Through

未找到 `epic-6-retrospective` 文档，因此无法对“Epic 6 承诺了什么、Epic 7 是否落实”做一一核账。这个断档本身就是一条重要学习：同一条产品线上的 follow-up epic 如果跳过 retrospective，流程改进会失去连续性。

不过，最近可用的 Epic 5 retrospective 已经提出过两类流程改进，它们在 Epic 7 仍然是显性问题：

1. story automator 的 source-of-truth 同步需要补强。
   Epic 7 结果：仍未彻底解决，review done 与 retrospective 状态都出现漂移。

2. enterprise 统一回归入口需要收敛。
   Epic 7 结果：仍以 story 级定向验证为主，还没有形成长期稳定的一键治理回归入口。

结论：Epic 5 的流程类 learnings 没有完全沉淀进 Epic 6/7 的日常执行，这解释了为什么 Epic 7 的主要摩擦仍然集中在自动化编排和回归组织方式上，而不是业务实现本身。

## Key Learnings

1. 企业治理 follow-up 功能最稳的实现方式，是复用既有事实源与服务，再追加新的投影和工作流，而不是为每个新需求再造一套状态模型。
2. 当全量测试信号不够干净时，团队必须把“定向验证命令 + 关键 story 证据 + commit + 状态同步”一起视为交付合同，缺一不可。
3. retrospective 不能只依赖自动会话；只要 story 证据已经齐全，就应该允许主流程直接按 source-of-truth 收口，而不是让子会话无限空转。
4. 对 enterprise 这条产品线来说，retrospective 已经不应该再被视为可有可无的附加步骤；它直接决定流程学习能不能跨 epic 延续。

## Significant Discoveries

本次 retrospective 识别出 3 项对后续工作有现实影响的发现：

1. Epic 7 的主要风险已经从“功能缺口”转移到“流程状态失真”。
   影响：如果不修正 automator 的收尾同步，后续团队会越来越难判断某个 enterprise epic 到底是“未完成”还是“状态没反写”。

2. enterprise governance 已经形成独立子系统，需要稳定回归入口。
   影响：后续只靠 story 级零散命令维持质量会越来越重，尤其是负责人权限、scope、预算委派、allocation lifecycle、quota request 和 governance timeline 之间已经形成强耦合。

3. 当前 `epics.md` 未定义 Epic 8。
   影响：暂时不存在必须立即更新的“下一 epic 计划”，但在继续推进 enterprise 工作之前，应该先明确下一轮是继续企业治理线，还是切换到其他产品线。

## Next Work Preview

## Final Summary

Epic 7 把 enterprise 模块真正推进到了“可治理”的阶段。负责人优先级、跨层预算委派、成员 allocation 生命周期、员工额度申请审批、治理时间线与钉钉通知已经形成闭环，产品能力层面的主要目标已经达成。

这次 retrospective 也把另一件事说得很清楚：当前最大的摩擦不在业务实现，而在 automator 的状态同步与回顾连续性。代码已经能交付，流程还需要补强。把这部分补齐，下一轮 enterprise 工作会顺很多。
