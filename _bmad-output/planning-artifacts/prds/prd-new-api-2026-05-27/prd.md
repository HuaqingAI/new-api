# PRD: `{NEW_PRODUCT_NAME}` V1 企业管控基线

*工作名待确认；文中 `{NEW_PRODUCT_NAME}` 沿用简报占位。*

> - **OQ-7：** 取消"主部门"概念，用户↔部门为 N:N 平等成员关系；任一部门独立向同一用户分配 wallet 子钱包；用量按成员视角重复计入，部门间不可加和。

## 0. 文档目的

本文档面向 PM、架构、UX、后续 story 拆分与实现团队，定义 `{NEW_PRODUCT_NAME}` V1 的企业管控基线需求。V1 当前覆盖组织/部门、钉钉登录与通讯录同步、部门级预算与用量看板、内容监控告警、分层预算治理与额度审批五类能力；V2 代码库 DeepWiki、WebChat 增强、多模态入口与 V3 SaaS 不进入本 PRD 的实现范围。技术方案细节、棕地代码约束和后续架构待决策项沉淀在同目录 `addendum.md`。

## 1. 愿景

`{NEW_PRODUCT_NAME}` V1 将现有 new-api 从以个人用户和单维 `Group` 为中心的 AI API 网关，升级为企业 IT 能治理、能分摊成本、能解释风险的 AI 中台基线。

V1 的核心赌注是：中国中型企业引入 AI 的首要阻力不再是“有没有模型入口”，而是“企业 IT 能否知道谁在用、哪个部门在花钱、额度是否会失控、出现违规时能否及时发现”。因此 V1 不追求新增模型能力或复杂知识库，而是先把组织身份、部门归属、部门预算、用量聚合与告警链路打通。

V1 成功后，企业管理员可以用钉钉组织树作为主要数据来源，让员工以企业身份登录 `{NEW_PRODUCT_NAME}`，按部门承接额度与统计口径，并在一个后台里回答“哪个部门花了多少 AI 额度、用在什么模型上、有没有触发内容风险”。

## 2. 目标用户

### 2.1 Jobs To Be Done

- 企业 IT 负责人要在不逐个手工维护用户组织关系的前提下，为公司开通可治理的 AI API 能力。
- 企业管理员要把 AI 额度分配到部门，并能证明部门级预算没有超额或漏算。
- 财务或业务负责人要看到部门维度的用量和成本归属，而不是只看到用户或模型级流水。
- 合规或安全负责人要在敏感词或内容风险出现时收到可追溯告警。
- 普通员工要使用企业身份登录后自动获得正确部门归属与可用额度，不需要理解底层渠道或计费配置。

### 2.2 非目标用户（V1）

- 不使用钉钉且要求完整本地组织管理后台的企业。该场景是否进入 V1 仍是开放问题。
- 需要 LDAP/SAML/SCIM 的企业客户。
- 需要 SaaS 多租户托管、公网注册、独立工作空间的客户。
- 需要代码库 DeepWiki、企业知识库 RAG、WebChat 多模态能力的研发团队。

### 2.3 关键用户旅程

- **UJ-1. 林工用钉钉组织树接入公司员工。**
  - **角色与场景：** 林工是中型企业 IT 管理员，已经在钉钉维护公司部门与成员。
  - **进入状态：** 林工以 Root 或管理员身份进入 `{NEW_PRODUCT_NAME}` 后台，系统尚未启用钉钉组织同步。
  - **路径：** 林工填写钉钉应用凭据并完成连通性校验；选择同步范围；触发首次同步；系统创建组织部门节点并把已有或新建用户关联到部门。
  - **价值时刻：** 林工在组织同步结果中看到同步成功、失败、跳过和冲突记录，并能打开部门树确认员工归属。
  - **结果：** 企业员工后续通过钉钉登录时会自动绑定到正确部门；同步异常可重新执行。
  - **边界情况：** 如果钉钉返回的用户缺少可用于匹配的手机号或邮箱，系统将该用户标记为待处理，而不是创建不可识别账号。

- **UJ-2. 王经理给研发部设置月度 AI 额度。** *(V1.1 修订)*
  - **角色与场景：** 王经理负责 AI 平台运营，需要把公司额度按部门分摊。
  - **进入状态：** 组织部门已同步，系统已有现行用户额度和 `Group` 倍率体系。
  - **路径：** 王经理进入部门预算页；选择研发部；创建一个 subscription 型预算池（月度周期）并设置 cycle_quota；然后从该池向团队成员分配 wallet 子钱包。
  - **价值时刻：** 系统明确显示研发部预算池剩余/已分配/周期生效状态，以及各成员子钱包的 remain_quota；员工在 API 消费时按子钱包优先级扣费，子钱包耗尽时该钱包不再参与扣费（可选：拒绝或切换到用户自有钱包，取决于优先级配置）。
  - **结果：** 研发部员工可以继续使用允许的模型，子钱包与自有钱包均耗尽时请求被阻止并给出明确原因。
  - **边界情况：** 如果员工同时属于研发部和数据部，两个部门可各自独立给该员工分配 wallet；两笔 wallet 并列存在于用户钱包列表中，按优先级消费；用量统计在两个部门都各计一次。

- **UJ-3. 陈总查看部门用量并导出报告。** *(V1.1 修订)*
  - **角色与场景：** 陈总需要向管理层说明 AI 成本如何分布。
  - **进入状态：** 系统已运行一段时间并产生消费日志与小时级用量聚合。
  - **路径：** 陈总进入组织用量看板；选择时间范围；按部门查看预算池/请求数/token/模型分布；导出 CSV。
  - **价值时刻：** 陈总能在同一视图里看到部门排行、模型成本分布和异常用量，CSV 与页面数字一致；页面与 CSV 均显式提示"部门间数值不可加和（多部门成员重复计入）"。
  - **结果：** 管理层能基于部门维度做预算调整或预算沟通；公司总用量取自用户/请求级原始口径，而非部门求和。
  - **边界情况：** 如果某用户在该时间范围内不存在任何部门成员关系，其消费归入"未归属"行，单独显示，不静默归入任何部门。

- **UJ-4. 赵安全收到内容风险告警并追溯请求。**
  - **角色与场景：** 赵安全负责企业 AI 使用合规。
  - **进入状态：** 系统启用了现有敏感词检查，并配置了告警收件人或钉钉通知目标。
  - **路径：** 某员工请求触发敏感词或内容风险；系统记录风险事件；发送告警；赵安全打开告警链接查看部门、用户、模型、时间和请求追踪 ID。
  - **价值时刻：** 赵安全能确认风险来自哪个部门，并在日志中定位上下文范围。
  - **结果：** 风险事件可追溯、可筛选、可统计。
  - **边界情况：** 如果通知通道不可用，系统保留事件记录并在后台显示发送失败原因。

- **UJ-5. 上级部门负责人向下级部门委派预算。** *(V1.3 Follow-up)*
  - **角色与场景：** 事业部负责人希望只控制总预算，不直接给每个员工分配额度。
  - **进入状态：** 企业组织树、部门预算池和负责人权限模型已经建立；上级部门拥有可用预算池，下级部门已有或即将创建自己的预算池。
  - **路径：** 上级部门负责人进入当前部门预算治理区；选择目标后代部门；从本部门预算池向目标部门预算池分配额度；下级部门负责人再在本部门上下文中继续向成员分配。
  - **价值时刻：** 上级负责人能看到“部门预算池 -> 部门预算池 -> 成员 wallet”的分层治理链路，而不需要越过下级负责人直接管理其成员。
  - **结果：** 企业预算形成“上级总额治理、下级自主细分”的闭环。
  - **边界情况：** 允许跨级分配到任意后代部门，但必须仍位于同一组织树祖先-后代链路内；预算池类型仍只允许使用既有 `balance` / `subscription`。

- **UJ-6. 员工额度不足时发起申请并由部门负责人审批。** *(V1.3 Follow-up)*
  - **角色与场景：** 员工在使用模型时额度不足，需要继续开展工作，但不应直接依赖全局管理员手工处理。
  - **进入状态：** 员工已登录并具备一个或多个部门成员关系；至少一个部门存在可用于分配的预算池；部门负责人或管理员可处理审批。
  - **路径：** 员工从余额 / 钱包相关入口发起额度申请；在申请表单中显式选择目标部门与目标预算池模式/池子；系统把申请路由给该部门的有效负责人；负责人在企业组织治理工作台中执行单步审批；审批通过后系统自动复用现有 allocation 能力完成分配并发送通知。
  - **价值时刻：** 员工无需理解底层计费主链路，也不需要等待管理员手工建钱包，即可通过标准治理链路获得额度。
  - **结果：** 企业在不引入复杂多级审批流的情况下，形成“申请 -> 审批 -> 自动分配 -> 审计 -> 通知”的最小闭环。
  - **边界情况：** 多部门成员必须显式选择目标部门与目标池子，避免审批归属歧义；若目标部门无有效负责人，申请回退给 Admin。

## 3. 术语表

- **`{NEW_PRODUCT_NAME}`** — 基于 new-api 的新产品发行名，占位符待替换；不得替换或删除 new-api 与 QuantumNous 受保护标识。
- **new-api** — 现有开源 AI API 网关代码基线，由 QuantumNous 维护。
- **企业** — V1 中使用 `{NEW_PRODUCT_NAME}` 自部署实例的客户组织；不等同于 SaaS 租户。
- **部门** — 企业组织树中的节点，主要来自钉钉通讯录同步。
- **成员关系 (department_membership)** — 用户与部门的 N:N 平等关联记录。V1.1 起取消"主部门"概念，一个用户可同时属于多个部门，任一部门都能独立向该用户分配预算。
- **部门预算（balance 型）** — 一次性总额型部门预算，可选过期时间；不周期重置，到期未用完按尽力回收策略归还父池。
- **部门预算（subscription 型）** — 周期型部门预算，与现有用户订阅同构（daily / weekly / monthly / custom_seconds），周期到点 `remain_quota = quota` 重置，复用现有 subscription_reset_task。
- **子分配 (sub-allocation / 子钱包)** — 部门向用户分配预算时，在目标用户名下创建的一行 `subscriptions` 记录，带 `source_type='enterprise_allocation'` 与 `source_allocation_id`。该行即用户的一个独立 wallet，与用户自有钱包并列。
- **wallet（钱包）** — 用户名下一行 `subscriptions` 记录的统一称呼。每个 wallet 独立持有 `quota / remain_quota / 周期 / 过期`，扣费按用户可调整的钱包优先级顺序进行。
- **铁律 (iron rule)** — `Σ children.committed_quota ≤ parent.total_quota / cycle_quota`，在创建、扩容、变更子分配前强制校验。
- **组织同步** — 从钉钉拉取部门与成员并写入 `{NEW_PRODUCT_NAME}` 本地组织模型的过程。
- **钉钉登录** — 员工使用钉钉 OAuth 完成身份认证并进入系统。
- **部门配额** — V1.1 改称"部门预算"，承载于 `enterprise_department_budgets`；区别于现有用户额度，且独立于 relay 计费链路。
- **用量看板** — 管理员查看部门维度请求数、token、额度消耗、模型分布的后台页面。V1.1 改为"按成员所属部门重复计入"口径。
- **内容风险事件** — 请求触发现有敏感词/过滤逻辑或 V1 扩展监控规则后产生的可追溯记录。
- **告警通道** — 用于发送内容风险或用量异常通知的邮件、钉钉机器人或 Webhook。
- **部门负责人** — 具有某个部门治理权限的角色来源。V1.3 同时支持钉钉同步负责人和手动指定负责人，两者并存时以本地显式覆盖优先。
- **包含子部门作用域** — 在查询/汇总场景中，把当前选中部门及其全部后代部门视为同一治理范围的可选口径；第一版优先用于预算 summary、用量 summary、告警 summary，不要求把所有明细列表扩成整棵子树。
- **预算委派 (budget delegation)** — 上级部门预算池向任意后代部门预算池分配额度的治理动作；不直接改变 relay 扣费链路，仍以预算池和 wallet 为治理载体。
- **额度申请 (quota request)** — 员工基于某个目标部门和既有预算池模式/池子提交的增额请求；审批通过后复用现有预算分配链路完成分配。
- **`Group`** — 现有 new-api 中用于计费倍率和可用渠道/模型选择的字符串标签；V1 不把它替换为部门。
- **服务账户 (service account)** — `users.type='service'` 的特殊账号，用于承载公共/共享额度（如 N8N），不对应自然人。

## 4. 功能需求

### 4.1 组织与部门模型

**描述：** 系统引入企业组织与部门层级，让用户可以与多个部门建立平等的成员关系（N:N），并让后续预算、用量和告警按部门聚合。组织模型必须兼容现有 `User.Group` 计费语义，不能把部门直接等同为 `Group`；V1.1 起取消"主部门"概念。[ASSUMPTION: V1 只有单企业自部署实例，不提供多企业运行时隔离。]

#### FR-1: 建立企业组织与部门层级

管理员可以查看由组织同步产生的部门树，每个部门包含稳定 ID、名称、父部门、状态和外部来源标识。实现 UJ-1、UJ-2、UJ-3。

> **V1.2 Follow-up（2026-05-31）：** 企业组织页后续迭代采用“左侧组织树 + 右侧当前部门工作区”的树驱动治理视图。当前选中部门是页面一级状态，而不是附属 detail drill-down；组织树需要定义展开/折叠、选中/高亮、默认展开和刷新恢复策略。详细交互骨架见 `addendum.md`。

**可验证结果：**
- 系统能保存至少 3 层部门结构，并保持父子关系稳定。
- 部门被钉钉删除或停用后，本地记录不会物理删除，历史用量仍可按旧部门名称追溯。
- 部门树查询能返回启用、停用和同步异常状态。

#### FR-2: 维护用户与部门的 N:N 成员关系 *(V1.1 修订)*

> **V1.1 变更：** 取消"主部门"概念。用户与部门为 N:N 平等关系，任一部门都可独立向同一用户分配预算（产生独立 wallet）；预算扣减发生在 wallet 而非部门，relay 路径不感知部门维度。

管理员可以在用户详情或组织视图中看到每个用户所属的全部部门成员关系，系统在登录、同步、用量统计中按所有成员关系展开使用，不存在"主部门"。实现 UJ-1、UJ-2、UJ-3。

**可验证结果：**
- 一个用户可同时拥有多个部门成员关系，任一部门都能独立向其分配 wallet（subscriptions 子钱包行），互不依赖。
- 用户加入或退出某部门后，新创建/被回收的成员关系不会修改其它部门已分配的 wallet；成员关系本身是 wallet 所有权的来源说明，不是计费载体。
- 用户没有任何部门成员关系时仍可按既有用户规则登录和使用，部门维度统计中显示为"未归属"。
- 任意 SQL/接口都不应假设"用户唯一部门"语义；早期文档中出现的"主部门"措辞均按 V1.1 解释为"该用户的某一项成员关系"。

#### FR-3: 保持部门与 `Group` 语义分离

系统必须保留现有 `Group` 对模型倍率、可用模型、渠道选择和订阅升级的作用；部门只用于组织归属、部门预算、部门统计和告警聚合。

**可验证结果：**
- 用户部门变更不会自动修改 `User.Group`。
- 现有按 `Group` 过滤渠道、模型和倍率的接口行为不因部门模型引入而改变。
- PRD/后续架构文档不得把部门命名为 group，以避免与数据库保留字处理和现有业务语义冲突。

#### FR-4: 预留 SaaS 租户演进字段

系统应在组织相关核心数据中预留 SaaS 演进所需的租户语义，但 V1 不开放多租户产品能力。[ASSUMPTION: V1 可以在数据模型中预留 `tenant_id`，默认固定为单租户值。]

**可验证结果：**
- V1 的组织、部门、用户部门成员关系、部门预算池、wallet 子分配和部门用量记录具备可迁移到租户维度的字段或映射策略。
- V1 UI 不出现 SaaS 工作空间、公共注册或跨租户管理入口。
- 架构评审必须确认该预留不会迫使 V1 为 SaaS 做额外流程让步。

### 4.2 钉钉登录与通讯录同步

### 4.3 部门预算与额度控制 *(V1.1 重写)*

**描述：** V1.1 在现有用户额度和计费体系之上，引入"部门预算池 + wallet 子分配"双层模型来实现部门级额度控制。

- **部门预算池** 承载在新表 `enterprise_department_budgets`，支持两种类型：
  - `balance`（一次性总额，可选 `expires_at`）
  - `subscription`（周期型，与现有用户订阅同构：`daily / weekly / monthly / custom_seconds`，周期到点 `remain_quota = quota` 重置，复用现有 `subscription_reset_task`）。
- **wallet 子分配** 是部门向用户分配预算的产物：在目标用户名下创建一行 `subscriptions` 记录（带 `source_type='enterprise_allocation'` 与 `source_allocation_id`）。这行子钱包与用户自有钱包并列，按用户可调整的优先级顺序参与扣费。
- **铁律：** `Σ children.committed_quota ≤ parent.total_quota（balance）` 或 `≤ parent.cycle_quota（subscription）`，在创建/扩容/变更子分配前强制校验。
- **不破坏现有计费：** relay 路径不感知部门维度，依然按 `User.Group` × 模型倍率 × 表达式系统结算 quota；部门预算仅通过 wallet 这一层影响扣费来源选择。

#### FR-9: 创建部门预算池 *(V1.1 修订)*

管理员可以为部门创建预算池，选择类型为 `balance` 或 `subscription`，并填写对应字段：

- `balance` 型：填写 `quota`，可选 `expires_at`；不周期重置。
- `subscription` 型：填写 `cycle_type`、`cycle_quota`、（`custom_seconds` 时填周期秒数）、起始时间；周期到点由复用的 `subscription_reset_task` 把 `remain_quota` 重置为 `cycle_quota`。

实现 UJ-2。

**可验证结果：**
- 未创建任何部门预算池时，系统保持现有用户额度与订阅扣费行为完全不变。
- 部门预算池保存时校验 quota / cycle_quota 为非负值，并记录管理员操作日志（含 `actor_id`、字段差异、生效时间）。
- 单个部门预算池实例一经创建不可在 `balance` 与 `subscription` 间切换；如需变更，必须先停用旧池并新建。
- 同一部门可创建多个预算池（例如一个长期 balance + 一个月度 subscription）；分配时管理员显式选择目标池。

#### FR-10: 以 wallet 子分配方式承接部门预算扣减 *(V1.1 重写)*

> **V1.1 核心变更：** V1.0 描述的"relay 预消费阶段先校验部门剩余额度并预扣"做法被取消。V1.1 不在 relay 路径插入任何部门维度判断；部门预算扣减统一通过 wallet 子分配落到用户名下，复用现有 subscription 钱包扣费链路。

管理员从部门预算池向某用户分配 wallet 时，系统在数据库同一事务中：

- (a) 减少父池 `remaining`（balance 型）或递增 `allocated_total`（subscription 型），并校验铁律；
- (b) 在目标用户名下创建一行 `subscriptions`，写入 `source_type='enterprise_allocation'`、`source_allocation_id`、周期/过期字段从父池继承；
- (c) 在 `enterprise_quota_allocations` 写入分配记录（含 `wallet_id` = 上面创建的 `subscriptions.id`，`status=active`），作为单一审计源。

实现 UJ-2。

**扣减时机（V1.1 验收基线）：**
- **预消费：** relay 路径继续按现有 subscription 钱包扣费逻辑工作，**不**新增任何"部门额度查询"。被分配出来的子钱包与用户自有钱包平等参与扣费，仅依用户可调整的钱包优先级顺序。
- **实际结算：** 上游响应返回后，按现有 subscription 钱包结算流程更新该 wallet 的 `remain_quota`；不需要把结算结果回写部门预算池，因为父池余额已在分配时一次性确定。
- **subscription 型重置：** 周期到点由现有 `subscription_reset_task` 把子钱包 `remain_quota` 重置为 `quota`，等价于父池在新周期对该用户的 REPLACE 语义；无新代码、无 relay 改动。
- **balance 型过期：** 子钱包带过期时间到达后，由后台 `balance_expiry_task` 按"尽力回收"策略将 `min(wallet.remain_quota, max(0, ...))` 归还父池 `remaining`，并把 allocation 标记为 `expired`。
- **父池状态联动：** 父池被暂停或过期时，由 `wallet_state_sync_task` 把所有子钱包同步置为暂停/失效，下次扣费时跳过该钱包；不立即物理删除子钱包，以保留审计。

**可验证结果：**
- relay 路径代码搜索 `relay/**` 不出现部门相关变量/查询；CI 中针对 `relay/` 的护栏检查通过。
- 部门预算被分配后，目标用户 `wallets` 列表中出现一行 `source_type='enterprise_allocation'` 的子钱包，其 quota / 周期 / 过期与分配参数一致。
- 父池剩余不足以容纳新分配时，分配接口返回明确错误码 `enterprise_budget_insufficient`（区分 `balance_remaining_insufficient` 与 `subscription_cycle_allocated_exceeded`），且数据库无副作用。
- 在 ≥50 并发、混合 `tiered_expr` 与固定计费模型的负载下，连续 ≥10 分钟运行后：子钱包累计 `consumed = quota − remain_quota`；父池 `Σ children.committed_quota ≤ parent.total_quota / cycle_quota` 永远成立；管理员强行重复分配或并发分配不出现父池负余额。
- subscription 型父池在周期重置时，所有从该池派生的有效子钱包 `remain_quota` 同步被 `subscription_reset_task` 重置；无需企业模块编写额外的重置代码。
- balance 型子钱包过期后，父池 `remaining` 增加值等于 `min(wallet.remain_quota_at_expiry, max(0, allocated_quota − consumed))`；同一过期事件被任务重跑不会重复回收（幂等）。

#### FR-11: 保留现有计费表达式和倍率语义 *(V1.1 调整措辞)*

系统继续使用现有模型计费、`Group` 倍率和计费表达式系统计算单次请求 quota；部门预算只通过 wallet 子钱包参与现有 subscription 扣费链路，不引入新的模型定价表达式，不在 relay 路径插入部门维度判断。

**可验证结果：**
- 使用 `tiered_expr` 模型时，子钱包扣减以结算后的 quota 为准，与从用户自有钱包扣费时完全一致。
- 不因部门预算引入新的表达式变量或改变 `p`、`c`、`len` 等计费表达式语义。
- 现有订阅套餐升级 `User.Group` 的行为不被部门预算覆盖；`User.Group` 与部门成员关系彼此独立。

#### FR-12: 展示部门预算与 wallet 状态 *(V1.1 修订)*

管理员可以查看每个部门预算池的当前状态以及由其派生的全部 wallet 子分配。实现 UJ-2、UJ-3。

> **V1.2 Follow-up（2026-05-31）：** 预算池查看、wallet 状态查看和预算分配必须从当前选中部门上下文进入，不再以输入 `Department ID` / `User ID` 作为主操作路径。企业组织页右侧工作区应直接承接当前部门的预算摘要、预算池列表、wallet 明细和分配操作。

**可验证结果：**
- 部门预算池列表可按使用率、剩余额度、类型（balance / subscription）、生效状态排序。
- 部门预算池详情展示：父池剩余 / 累计已分配 / 派生子钱包列表（目标用户、quota、remain_quota、周期/过期、状态）。
- 预算池列表、预算池详情与派生子钱包列表在保留 quota 原值的同时，补充金额（$）显示；若当前上下文缺少可靠金额换算信息，至少保留 quota 原值并对金额显示做显式兜底。

- 列表与详情严格基于 `enterprise_department_budgets` 与 `enterprise_quota_allocations` 的当前快照，不读取 `logs` 表。
- 临近耗尽状态分两档：**预警**（默认使用率 ≥ 80%）和**紧急**（默认使用率 ≥ 95%）；两档阈值在产品设置中可调整，调整保存时校验 `0 < 预警 < 紧急 ≤ 100`。

- CSV 字段固定按以下顺序输出：`部门 ID`、`部门名称`、`父部门`、`周期开始`、`周期结束`、`请求数`、`prompt_tokens`、`completion_tokens`、`quota`、`用户数`。
- CSV 行集合等于页面当前筛选条件下聚合后的部门集合，包含"未归属"行（部门 ID 为空、部门名称为 `未归属`）；每一数值与页面对应单元格相等。
- 导出文件首行（标题行之前）包含一行注释行：`# 注意：用量按用户当前所属部门重复计入，部门间数值不可加和`，下游消费方可解析或忽略。
- 行排序与页面当前排序一致；空值统一输出为空字符串，不输出 `null`。
- 导出操作记录管理员操作日志，包含筛选条件快照与行数。

#### FR-16: 发送定期用量报告

系统可以按配置向指定邮箱发送部门用量报告。[ASSUMPTION: V1 定期报告优先使用现有邮件能力；钉钉机器人报告作为可选告警通道，不作为 V1 报告必需项。]

**可验证结果：**
- 管理员可以配置报告接收人、频率和时间范围。
- 邮件发送失败会记录失败原因，并不影响看板数据生成。
- 报告至少包含部门总览、Top 部门和异常高增长部门。

### 4.5 内容监控告警

**描述：** V1 基于现有敏感词检查与过滤能力补充事件记录和通知闭环，让企业能看到部门维度的风险事件。V1 不承诺复杂语义审核或第三方内容安全模型。

#### FR-17: 记录内容风险事件 *(V1.1 修订)*

当请求触发现有敏感词检查或过滤规则时，系统记录内容风险事件，包含用户、用户当时的部门成员关系列表、模型、时间、请求追踪 ID、风险类型和处理结果。实现 UJ-4。

> **V1.2 Follow-up（2026-05-31）：** 风险事件、风险筛选和相关企业页面中的用户展示，统一遵循“可读名称优先，username / ID 兜底”的规则，以保证组织页、预算页、用量页与风险页对同一对象的识别方式一致。

**可验证结果：**
- 风险事件保存请求发生时的部门成员关系快照（多部门以列表存储），筛选时按"包含某部门"语义命中，与 FR-13 / FR-20 的"重复计入"口径一致。
- 风险事件可按部门、用户、模型、风险类型和时间范围筛选。
- 风险事件不在普通用户日志中暴露管理员专用字段。
- 风险事件保留必要追溯信息，同时遵守现有日志脱敏策略。

#### FR-18: 配置告警规则和告警通道

管理员可以配置内容风险告警规则、接收人和告警通道。实现 UJ-4。

**可验证结果：**
- 支持至少邮件告警；钉钉机器人或 Webhook 是否作为 V1 必选见开放问题 OQ-4。
- 告警规则可以按风险类型和部门范围启用或停用。
- 告警配置保存时校验接收人或 Webhook 格式，并记录管理员操作日志。

#### FR-19: 发送可追溯告警通知

触发告警规则时，系统发送通知并提供能定位后台事件详情的追溯信息。实现 UJ-4。

**重试策略（V1 默认）：**
- 同一告警通知在通道返回失败时按指数退避重试 3 次（首次 30 秒、其后 2 分钟、10 分钟），3 次后标记为最终失败。
- 最终失败的告警在后台告警发送列表中保留可见，并提供"重新发送"操作；重新发送计为新一轮投递，不重置原事件追溯。
- 同一风险事件在 5 分钟内重复触发同一告警规则时，按事件聚合为一次告警发送，避免噪声。

**可验证结果：**
- 告警内容至少包含部门、用户、模型、时间、风险类型、请求追踪 ID。
- 通知发送状态可查询且区分：待发送、发送成功、发送失败（带错误原因）、最终失败、已重发。
- 通知失败不会阻止风险事件落库。
- 后台可对最终失败的告警手动一键重发，并标记本次为人工触发。

#### FR-20: 展示部门风险概览 *(V1.1 修订)*

管理员可以在组织用量或监控页面查看部门风险次数、风险率和近期趋势。实现 UJ-3、UJ-4。

> **V1.2 Follow-up（2026-05-31）：** 部门风险概览与后续企业页面中的用户展示规则保持一致：优先展示可读名称，必要时回退到 username / ID；页面骨架和树状态模型复用企业治理视图的统一定义。

**可验证结果：**
- 风险率定义：在所选时间范围内，`风险率 = 该部门成员触发风险事件的请求数 ÷ 该部门成员请求总数`；被拦截的请求同时计入分子与分母；N:N 多部门成员关系下同一笔请求会在多个部门分别计入（"重复计入"口径，与 FR-13 / FR-14 一致）。未归属用户的请求不纳入任何部门的风险率，单独显示。页面以 tooltip 或同位文案展示该公式，并在多部门场景下附注『部门间数值不可加和』免责说明（i18n key `enterprise.usage.multi_dept_disclaimer`）。
- 支持查看 Top 风险部门和风险事件列表。
- 部门风险统计与风险事件明细数量一致。

### 4.6 分层预算治理与额度审批 *(V1.3 Follow-up)*

**描述：** 在既有企业组织、部门预算池、成员 wallet 分配、用量看板和告警能力基础上，新增治理层闭环：部门负责人权限模型、包含子部门的查询作用域、上级预算池到下级预算池的分层委派、成员 allocation 调整/取消/回收、员工额度申请与单步审批、治理动作审计与钉钉通知。该闭环属于企业模块增强，不改 relay、billing expression 和现有 quota 结算主链路。

#### FR-21: 建立部门负责人权限模型

系统支持同时使用钉钉同步负责人和手动指定负责人作为部门治理权限来源。两者并存时，推荐优先级为 `manual_deny_override > manual_grant > dingtalk_synced_owner`，以本地显式覆盖结果作为最终生效权限。实现 UJ-5、UJ-6。

**可验证结果：**
- 同一部门可以同时记录钉钉同步负责人事实和本地手动授权记录，且两类来源可审计。
- 手动显式禁用优先于手动授权，手动授权优先于钉钉同步负责人。
- 不扩展 `users.role` 枚举；负责人权限仍落在企业部门角色/成员关系体系内。
- 若部门无任何有效负责人，治理动作可回退到 Admin，但必须有明确的错误提示或回退说明。

#### FR-22: 支持包含子部门的查询作用域

系统在预算 summary、组织用量 summary、告警 summary 等查询/汇总场景中，支持“仅当前部门”与“包含子部门”两种作用域。第一版优先覆盖 summary / overview 视图，不要求把所有明细列表扩展成整棵子树。实现 UJ-3、UJ-5、UJ-6。

**可验证结果：**
- 查询接口支持显式的 `include_descendants` 或等价布尔参数。
- 默认口径保持“仅当前部门”，用户可切换为“包含子部门”。
- 作用域切换后，预算汇总、用量汇总和告警汇总数据按祖先-后代树链聚合。
- 为保证三库兼容，第一版继续使用邻接表；如性能需要可增加路径缓存字段，但 V1.3 不引入闭包表。

#### FR-23: 支持上级预算池向下级部门预算池分配

系统支持上级部门负责人把本部门预算池中的额度分配给任意后代部门预算池，不限制为直属下级。该能力继续复用现有 `balance` / `subscription` 预算池模型，不新增新的预算类型。实现 UJ-5。

**可验证结果：**
- 祖先部门可向任意后代部门预算池分配预算，但不得越过组织树边界分配到无祖先-后代关系的部门。
- 预算池类型仍只允许 `balance` 与 `subscription`；不引入第三类预算策略。
- 上级到下级预算池的分配动作保留完整审计链，至少记录来源池、目标池、操作者、分配额度、类型快照和状态。
- 预算池调整优先按“关闭旧分配 + 新建新分配”建模，不静默覆盖历史委派记录。

#### FR-24: 补齐成员 allocation 的调整、取消与回收治理

系统为成员额度分配补齐调整、取消和回收能力。调整优先按“关闭旧分配 + 新建新分配”建模；取消不做硬删除，保留 `active / superseded / revoked / expired / closed` 等状态语义。实现 UJ-2、UJ-5、UJ-6。

**可验证结果：**
- 调整成员 allocation 时，旧 allocation 保持可追溯，新 allocation 承载新的额度事实。
- 取消不物理删除 wallet 或 allocation，而是进入明确状态并保留审计。
- 回收动作记录回收额度、操作者、处理时间和来源 allocation。
- 现有 `wallet_state_sync_task`、`balance_expiry_task` 和 wallet 生命周期规则继续生效，不新增 relay 扣费逻辑。

#### FR-25: 支持员工额度申请与单步审批

当员工额度不足时，允许其从余额 / 钱包相关入口发起额度申请。申请表单中必须显式选择目标部门和基于现有企业预算池能力的模式或目标池；审批为单步，由目标部门的有效负责人集合处理，审批通过后系统自动复用现有预算分配能力完成分配。企业组织页保留审批与治理视图，但不是普通员工唯一入口。实现 UJ-6。

**可验证结果：**
- 员工提交申请时必须显式选择目标部门和目标预算池模式/池子，避免多部门成员关系下的审批归属歧义。
- 员工提交申请时，预算池选项必须至少同时展示部门名、预算池标识或名称、预算类型、当前可分配/剩余额度与状态；完成选择后，界面必须显示“已选请求范围/已选预算池摘要”。
- 额度申请相关表单支持 quota / 金额（$）视角切换；该切换首先是显示/输入层能力，不改变后端底层 quota 存储模型。
- 审批流程为单步，不做多人会签、代理审批、复杂升级链。
- 若预算不足，本轮允许审批人驳回或按较小额度批准，不要求升级审批链。
- 审批通过后，系统直接复用既有预算分配链路完成自动分配，不新发明第三套额度生命周期规则。
- 申请、审批、自动分配和结果通知必须具备幂等保护，避免重复审批导致重复分配。

#### FR-26: 建立治理动作审计与钉钉通知闭环

系统对部门负责人授权、跨层预算委派、成员 allocation 调整/取消/回收、员工申请审批、自动分配和回收等动作形成统一审计与钉钉通知闭环。实现 UJ-5、UJ-6。

**可验证结果：**
- 审计至少覆盖授权来源、操作者、目标对象、额度变化、处理时间、动作状态和追溯 ID。
- 钉钉通知优先覆盖：申请提交、审批通过、审批拒绝、分配成功、回收/撤销。
- 通知失败不会阻止核心治理事务提交，但必须记录投递状态和错误原因。
- 治理动作结果与通知投递结果必须独立记录和独立展示。审批通过、自动分配成功等核心治理动作，不得因为通知未配置或通知投递失败而在产品上被呈现为治理动作失败。
- “未配置治理通知通道/无可用通道”必须与“投递失败”区分，不得共用失败语义。
- 审计链路能把“部门预算池 -> 下级预算池 -> 成员 wallet -> 申请/审批结果”串联起来。

## 5. 非目标

- V1 不交付代码库 DeepWiki、通用企业文档库 RAG、WebChat 增强或多模态生成入口。
- V1 不交付 SaaS 多租户、公网注册、工作空间、租户计费或跨租户隔离。
- V1 不交付 LDAP、SAML、SCIM。
- V1 不交付飞书或企业微信登录，只做同模式结构预留。
- V1 不交付私有化授权 License 机制。
- V1 不新增专用审计日志表，除非架构评审证明现有 `Log` 与 `admin_info` 无法满足本 PRD 的操作追溯。
- V1 不把部门替代现有 `Group`，不重写现有模型倍率、分组倍率或分组间倍率体系。

## 6. MVP 范围

### 6.1 范围内

- 单企业自部署实例下的组织与部门模型。
- 用户与部门的 N:N 平等成员关系（V1.1）。
- 钉钉 OAuth 登录。
- 钉钉通讯录全量/定时同步。
- 部门预算池（balance / subscription 双类型，V1.1）配置、铁律校验、wallet 子分配与状态展示。
- 部门用量聚合看板、详情和 CSV 导出（多部门重复计入口径，V1.1）。
- 基于现有过滤能力的内容风险事件、告警和部门风险概览。
- 部门负责人权限模型、包含子部门的 summary 作用域、预算委派、成员 allocation 治理、员工额度申请与单步审批、治理审计与钉钉通知（V1.3 Follow-up）。
- 三库兼容的数据模型和迁移。

### 6.2 MVP 范围外

- 本地组织管理 UI：仅作为开放问题确认，不默认进入 V1。
- 部门间用量加和与"全公司唯一权威值"：V1.1 看板按成员视角重复计入，部门间不可加和；公司总用量取自用户/请求级原始口径。
- 多部门加权分摊（按比例切片到各部门）：V1.1 不实现，未来可在 wallet 上叠加权重字段实现。
- 复杂多级审批、代理审批、会签流：V1.3 只做员工额度申请、部门负责人单步审批与自动分配，不扩展复杂审批链。
- 复杂内容安全模型：V1 只增强现有过滤与事件通知闭环。
- 上游开源贡献节奏：按 case 决定，不设 PRD 成功指标。

## 7. 成功指标

**Primary**

- **SM-1:** 至少 1 家企业在生产或准生产环境完成钉钉登录、部门同步、部门级用量看板（含『部门间不可加和』口径）闭环验证，且连续 14 天可正常同步。验证 FR-5、FR-6、FR-7、FR-13。
- **SM-2:** 部门级预算（balance / subscription）与 wallet 子分配在生产环境连续 30 天无超额、漏算或父池负余额事故。验证 FR-9、FR-10、FR-11、FR-12。
- **SM-3:** 管理员能在 5 分钟内从部门用量看板定位某部门的主要模型消耗，并导出一致的 CSV。验证 FR-13、FR-14、FR-15。

**Secondary**

- **SM-4:** 内容风险事件触发后，告警通知或后台事件记录在 1 分钟内可见。验证 FR-17、FR-19。
- **SM-5:** 首次钉钉全量同步结果中的失败项具备可操作错误原因，管理员无需查服务器日志即可判断下一步。验证 FR-7、FR-8。

**Counter-metrics（不要优化错方向）**

- **SM-C1:** 不以“同步覆盖用户数最大化”为单一目标；错误绑定比未绑定更危险，无法可靠匹配的员工必须进入待处理。
- **SM-C2:** 不以“部门预算拦截次数越多越好”为目标；预算拦截是治理能力，不是业务价值。
- **SM-C3:** 不以“告警数量越多越好”为目标；告警必须可追溯、可分流，避免噪声导致管理员关闭告警。

## 8. 跨切面 NFR

- **兼容性：** 新增数据库对象和查询必须同时兼容 SQLite、MySQL 5.7.8+、PostgreSQL 9.6+。
- **安全：** 钉钉应用密钥、Webhook、邮箱凭据等敏感配置不得明文返回前端，不得写入普通日志。
- **隐私：** 内容风险事件默认只展示追溯所需摘要，不扩大现有日志中敏感内容的可见范围。
- **可靠性：** 组织同步失败不得影响现有登录、API 调用、计费和日志链路。
- **一致性（V1.1 修订）：** 部门预算 wallet 子分配的扣减必须与用户 quota 消费最终一致；铁律 `Σ children.committed_quota ≤ parent.total_quota / cycle_quota` 在分配/扩容前强制校验，不能出现父池负余额或"用户扣费成功但部门 wallet 未同步扣减"。
- **可观测性：** 同步任务、配额拦截、告警发送必须有后台可查状态和错误原因。
- **性能：** 部门用量看板默认时间范围查询不得依赖逐条扫描全量日志；V1 验收基线设为：在 `logs` 累计 100 万条、部门数 ≤ 100 的环境下，"近 30 天部门用量"页面首屏数据返回 < 3 s（P95）。如需聚合表或快照表，架构阶段明确。[ASSUMPTION: 该阈值是 V1 起步基线，可由架构阶段根据所选实现路径调整，但调整必须更新本 NFR。]
- **国际化：** 新增前端文案必须进入 `web/default/src/i18n/locales/{lang}.json`，以英文 key 作为源字符串，并保持现有多语言同步流程。

## 9. 约束与护栏

- 所有 JSON marshal/unmarshal 操作必须使用 `common/json.go` 中的封装函数；不得在业务代码中直接调用 `encoding/json` 的 marshal/unmarshal。
- 数据库保留字列处理必须沿用现有 `commonGroupCol`、`commonKeyCol` 等模式；不要新增名为 `group` 的组织字段。
- 组织和部门模型不得破坏现有 `User.Group`、`Token.Group`、渠道分组和计费倍率语义。
- 如果部门预算触及结算链路，必须保持计费表达式系统“一条表达式定义模型计费”的原则；V1.1 起部门预算只通过 wallet 子钱包参与现有 subscription 扣费链路，relay 路径不感知部门维度。
- `new-api` 和 `QuantumNous` 是受保护标识，不得删除、替换或改名。
- V1 以企业自部署为优先，不为 SaaS 公网注册或跨租户运营牺牲当前交付。

## 10. 集成与依赖

- **钉钉开放平台：** OAuth 登录、通讯录部门、成员数据与应用权限配置。
- **现有 OAuth 体系：** 需要决策钉钉登录复用 `CustomOAuthProvider` 还是新增专用 provider。
- **现有用户体系：** `model.User` 当前以 `Group`、quota、角色和多种外部账号字段承载用户身份。
- **现有计费与日志体系：** 用户 quota、`Log`、`QuotaData`、计费表达式、数据导出能力是部门预算与看板的基础；V1.1 部门预算 wallet 子分配直接复用现有 `subscriptions` 表与 `subscription_reset_task`。
- **现有敏感词配置：** `setting/sensitive.go` 与 relay 请求检查是内容风险事件的基础。
- **现有通知能力：** 邮件发送能力已存在；钉钉机器人/Webhook 是否进入 V1 必选需确认。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 钉钉通讯录数据与本地账号匹配不可靠 | 错绑账号比无法登录更严重 | 无可靠唯一标识时进入待处理；同步结果暴露冲突列表 |
| 部门预算 wallet 子分配与用户 quota 双重扣减产生不一致（V1.1） | 账务可信度下降 | 分配时在事务内同时扣父池/建子钱包/写审计；铁律 `Σ children ≤ parent.total/cycle_quota` 在分配/扩容前强制校验；并发扣减必须有测试 |
| 多部门重复计入引发管理层误解（V1.1 新增） | 把部门和当成总用量 | 看板/详情/CSV/告警强制展示"部门间数值不可加和"免责说明（i18n key `enterprise.usage.multi_dept_disclaimer`）；CSV 含注释行 |
| 父池暂停/过期未联动子钱包（V1.1 新增） | 子钱包继续扣费导致父池语义失效 | 由 `wallet_state_sync_task` 周期巡检父池状态并同步置位子钱包；不物理删除以保留审计 |
| `tenant_id` 预留过早扩大改造面 | V1 拖期 | 只在组织相关新表预留，是否扩展到旧表作为开放问题单独评审 |
| 看板按部门聚合拖慢日志查询 | 管理后台不可用 | 使用聚合表、快照或异步任务；避免默认扫全量日志 |
| 告警噪声过高 | 管理员关闭告警 | 默认低频、可配置阈值、事件可追溯 |
| 本地组织 UI 被临时纳入 V1 | 6-8 周目标失控 | 将其作为 Plan B 开放问题，不在默认 MVP 范围内 |

## 12. 发布与验收

- **V1 目标交付窗口：** 约 6-8 周（来自简报）。窗口失控时优先压缩范围而非延期 SaaS / V2 内容。
- **Alpha（内部验证）：** 本地或测试环境完成组织模型、钉钉登录、手动同步和基础部门树展示。
- **Beta（试点企业）：** 1 家试点企业完成钉钉同步、部门预算（balance / subscription 双类型）与 wallet 子分配、部门看板，收集预算口径、wallet 优先级、多部门重复计入的反馈与同步异常。
- **V1 验收：** 达成 SM-1、SM-2、SM-3；开放问题中所有 V1 阻塞项已关闭或有明确延后记录。

## 13. 开放问题

- **OQ-1:** 产品名是否在 V1 PRD 定稿前确认，还是继续使用 `{NEW_PRODUCT_NAME}` 占位进入架构与 story？
- **OQ-2:** V1 是否必须包含“无钉钉时的本地组织管理 UI”？默认不包含，但这是不用钉钉客户的 Plan B。
- **OQ-3:** `tenant_id` 是否只在新增组织相关表预留，还是 V1 就扩展到 `users`、`logs`、`quota_data` 等旧表？两条路径的取舍：

  | 选项 | V1 工期影响 | 迁移与索引改造 | SaaS 切换代价 |
  |---|---|---|---|
  | A. 只在新增表预留（PRD 默认假设） | 新增 6-9 张表 schema，沿用现有 `users`/`logs`/`quota_data` 不动 | 仅新表内增加 `tenant_id` 索引；现有 GORM 查询零侵入 | V3 切换 SaaS 时需为 `users`/`logs`/`quota_data` 做带租户隔离的迁移 + 历史回填 + 查询路径改造 |
  | B. V1 即扩展到旧表 | 新增表 + 改 3+ 张核心表 schema、迁移、所有 GORM 查询需带租户过滤；估增 1-2 周 | 三库迁移工作量翻倍；`logs`/`quota_data` 海量数据需要分批回填策略；新增组合索引 | V3 切换 SaaS 时迁移面接近零，重在租户边界的代码审计 |

  V1 默认选 A；选 B 必须先获得 V3 SaaS 立项确认与额外工期预算。
- **OQ-4:** 钉钉机器人/Webhook 告警是否为 V1 必选，还是 V1 只保证邮件告警和后台事件？
- **OQ-5:** 钉钉登录应复用现有 `CustomOAuthProvider`，还是新增钉钉专用 OAuth provider 与通讯录同步模块？
- **OQ-6:** ~~部门配额周期只支持自然月，还是支持自定义周期起止？~~ *【V1.1 已关闭，2026-05-27】* — 决议：部门预算同时支持 `balance`（一次性总额，可选 `expires_at`，不周期重置）与 `subscription`（周期型，与现有用户订阅同构，支持 `daily / weekly / monthly / custom_seconds`，周期到点 `remain_quota = quota` 重置，复用现有 `subscription_reset_task`）两种类型。详见 FR-9 / FR-10、§14 假设与架构文档 V1.1 CP-5。
- **OQ-7:** ~~员工存在多个钉钉部门时，主部门来源规则由钉钉主部门字段、管理员配置还是首次同步结果决定？~~ *【V1.1 已关闭，2026-05-27】* — 决议：取消"主部门"概念。用户与部门为 N:N 平等成员关系，任一部门可独立向同一用户分配 wallet 子钱包；用量统计采用"成员视角重复计入"，部门间数值不可加和。详见 FR-2 / FR-13 / FR-14 / FR-20 与架构文档 V1.1 CP-2 / CP-14。

## 14. 假设索引

- §4.1 — [ASSUMPTION] V1 只有单企业自部署实例，不提供多企业运行时隔离。
- §4.1 FR-4 — [ASSUMPTION] V1 可以在数据模型中预留 `tenant_id`，默认固定为单租户值。
- §4.3 FR-10 — [ASSUMPTION, V1.1 修订] 部门预算扣减不在 relay 路径发生。分配时在数据库事务中一次性从父池扣减到目标用户名下 wallet（subscription 行），relay 路径复用现有 subscription 钱包扣费链路。并发安全由铁律校验 + 行级锁保障（CREATE 时 `Σ children + new ≤ parent.total/cycle_quota`），具体机制由架构 V1.1 §4 确定。
- §4.4 FR-16 — [ASSUMPTION] V1 定期报告优先使用现有邮件能力；钉钉机器人报告作为可选告警通道，不作为 V1 报告必需项。
- §8 NFR 性能 — [ASSUMPTION] 100 万条 `logs` / ≤100 部门下"近 30 天部门用量"首屏 < 3 s（P95）是 V1 起步基线，可由架构阶段调整，但调整必须更新本 NFR。
