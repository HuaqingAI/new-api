# PRD Quality Review — `{NEW_PRODUCT_NAME}` V1 企业管控基线 PRD

## Overall verdict

PRD 整体落地度高：四条 UJ 都有命名主角与边界处理，FR 与 UJ 双向引用，棕地代码引用（`User.Group`、`commonGroupCol`、`setting/sensitive.go`、计费表达式系统）经抽查与代码一致，FR-3 / FR-11 守住了"部门 ≠ Group"和"部门只消费 quota"两条最容易出错的边界。立得住的部分集中在范围诚实度与下游可用性。最大风险集中在 Done-ness：愿景虽点出"中国中型企业 + 钉钉接入"的赌注，但若干 FR 的"可验证结果"仍藏在"明确"、"可区分"、"可操作"之类形容词里；FR-10 把并发安全表述为"不能造成超扣或漏扣"但不给口径，而 addendum A-4 已点名这是验收风险最高项；SM-1 用"至少 1 家企业"是诚实但样本极小的指标，14/30 天窗口与"6-8 周交付"并未在 PRD 内对齐。决策层面 OQ-3（`tenant_id` 是否扩到旧表）是真正的取舍，PRD 给了默认假设但没把"扩旧表"的代价量化，建议进入 story 前先关掉。

## Decision-readiness — adequate

PRD 在多处把决策"做了"而不是"模糊掉"——FR-3 直接禁止把部门命名为 group，FR-11 明确部门只消费结算 quota，§5 非目标列表逐条点名 SaaS / LDAP / DeepWiki / 飞书企微 / License / 专用审计表，§9 把"不为 SaaS 公网注册牺牲 V1 交付"写成护栏。这些都是真决策。

但有两个真正的张力被推到 OQ：OQ-3（`tenant_id` 预留到新表 vs 旧表）是 V1 / V3 的取舍点，addendum A-2 已说明"扩旧表显著增加迁移、查询和索引改造成本"，但 PRD 主体只在 FR-4 写下"假设只在新增表预留"，没有让决策者看到"如果选扩旧表，V1 工期/复杂度的代价是什么"——一个决策者读完 OQ-3 仍然无法判断。OQ-2（无钉钉企业的本地组织 UI）通过 §11 风险表点出"6-8 周目标失控"做了反对面，但"6-8 周"从未在 PRD 主体出现，依赖外部简报，本 PRD 无法独立判断。OQ-5（钉钉登录复用 `CustomOAuthProvider` 还是新增专用 provider）是架构选择，留给架构阶段是合理的，但 OQ-6（部门配额周期）和 OQ-7（多部门员工的主部门来源规则）会直接决定 FR-9 / FR-2 的可验收口径，应在故事拆分前关掉。

7 条 OQ + 3 条 ASSUMPTION 对一个被定位为"绿灯进入架构与 story"的 PRD 偏多；不至于 broken，但提示决策密度不足。

### Findings

- **high** OQ-3 没有让取舍可比较 (§13 OQ-3 / §4.1 FR-4 / addendum A-2) — OQ 只问"是否扩到旧表"，PRD 主体没有把两条路径在 V1 工期、迁移成本、索引改造、SaaS 切换难度上的代价摆出来。决策者读完仍要回到 addendum 才能判断。*Fix:* 在 §4.1 FR-4 或 §13 OQ-3 下增补两行表格："只新表预留：V1 +X 张表 schema，SaaS 切换需补 Y。扩到旧表：迁移影响 `users`/`logs`/`quota_data`，索引改造 Z 项。"让决策可读。
- **medium** OQ-6 / OQ-7 决定 FR 验收口径却被推迟 (§13 OQ-6, OQ-7 / §4.3 FR-9 / §4.1 FR-2) — FR-9 "周期配额"未定义周期是自然月还是自定义，FR-2 "主部门"未定义来自钉钉主部门字段还是首次同步。两个问题都进入 V1 故事拆分前必须解决，否则 acceptance 写不实。*Fix:* 在进入 epic/story 之前由 PM 与 IT 林工对齐两条规则，回填到 FR-9 和 FR-2 的"可验证结果"。
- **low** "6-8 周交付窗口" 未在 PRD 内出现 (§11 风险表 / §6 MVP) — 风险表第 6 行写"6-8 周目标失控"暗示有窗口约束，但 PRD 主体未声明 V1 时间盒。读者只能从 brief 推断。*Fix:* §6 MVP 或 §12 发布与验收增一句"V1 目标交付窗口约 X 周（来自 brief）"。

## Substance over theater — strong

四个 UJ 都不是装饰：UJ-1 林工带出"无可靠匹配标识进入待处理"，UJ-2 王经理带出"多部门员工只走主部门"，UJ-3 陈总带出"历史日志缺部门快照应显示未归属而非反推",UJ-4 赵安全带出"通知失败不阻断事件落库"——四条边界情况都直接转化为对应 FR 的"可验证结果"或非目标项，没有装样子的角色。愿景段第二段（§1）专门点出"中国中型企业 + 钉钉为优先入口"，与"通用企业 AI 治理"区分开，不是可以无差别套用的句式。NFR（§8）八条都给了具体动作（"必须同时兼容 SQLite/MySQL 5.7.8+/PostgreSQL 9.6+"、"看板默认时间范围查询不得依赖逐条扫描全量日志"），不是"系统必须可扩展"式 NFR theater。SM 段配套了 SM-C1..SM-C3 反向指标，对治理类产品尤其重要——counter-metric 写得很到位（"错误绑定比未绑定更危险"、"配额拦截是治理能力，不是业务价值"、"告警必须可追溯避免噪声"）。

## Strategic coherence — strong

PRD 有清晰的赌注（§1 第二段："中国中型企业引入 AI 的首要阻力不是有没有模型入口，而是企业 IT 能否知道谁在用、哪个部门在花钱"），五大 FR 子节（4.1 组织模型 / 4.2 钉钉 / 4.3 部门配额 / 4.4 看板 / 4.5 内容监控）都直接服务这个赌注，没有"backlog with section headings"的味道。FR-3 / FR-11 / 护栏 §9 共同守"不替换现有 Group 与计费表达式语义"这条主轴。SM-1（部门同步连续 14 天）、SM-2（30 天无超额漏算）、SM-3（5 分钟定位）覆盖三大主能力，且都不是 DAU/MAU 式活动量指标——SM-2 直接验证"额度可信"这一治理价值。MVP 范围（§6）与非目标（§5）边界一致，没有把 V2 / V3 内容漏进 V1。

## Done-ness clarity — thin

这是 PRD 最该被 unforgiving 的维度，也是最薄的一项。结构上每条 FR 都有"可验证结果"小节，但若干条仍藏在形容词里：

- FR-5 "连通性测试返回认证成功、权限不足、网络失败、回调配置错误等可区分结果"——"可区分"未规定错误码或可观测形态，story 写 acceptance 时要回头补。
- FR-10 "并发请求不能造成部门配额超扣或漏扣" / "实际结算与预估消费存在差异时，部门用量与用户用量最终一致" ——这是 addendum A-4 直接点名的"验收风险最高"项，PRD 没给出 "在 N 并发、M 部门、K 模型下连续 X 分钟无负数剩余" 之类可执行的验证命题，留给架构。FR-10 是最要补的 FR。
- FR-6 "登录成功后，用户的主部门与最近一次有效同步结果一致"——"一致"对一个长事件链（OAuth 回调 + 同步任务 + 主部门挑选）含义不清，是当次登录读最新还是同步任务最近成功结果，应明确。
- FR-12 "接近耗尽状态阈值可配置，默认阈值在产品设置中明确"——把阈值 punted 到"产品设置"未给默认。
- FR-15 "CSV 中数值与页面当前筛选结果一致"——一致是逐字节、聚合一致还是允许排序差，未定。
- FR-19 "通知发送成功、失败、重试状态可查询"——重试策略（次数、间隔、终态判定）未定，story 拆到 retry 任务时无依据。
- FR-20 风险率 "在页面说明统计口径"是产品要求，但 PRD 没给口径定义文字（同期 / 滚动窗口？）。

NFR 段（§8）"性能"项写"看板默认时间范围查询不得依赖逐条扫描全量日志"是好的边界，但没有给响应时间或数据量阈值，story 阶段无法定 SLA。

### Findings

- **critical** FR-10 部门配额并发安全无可执行验证命题 (§4.3 FR-10) — addendum A-4 已说"FR-10 验收风险最高，应优先出技术设计和并发测试"，但 FR-10 仅写"不能造成超扣或漏扣"。这是 PRD 的核心治理承诺，下游 story 据此写不出 acceptance。*Fix:* 增加"在 ≥N 并发、跨同部门 M 个用户、含 `tiered_expr` 模型的混合负载下，连续 X 分钟无部门剩余额度负数、无用户 quota 与部门 quota 终态偏差超过 ε"之类量化条件；并明确预消费 vs 结算两条路径上的扣减时机（addendum A-4 已枚举候选）。
- **high** FR-6 主部门一致性时机未定 (§4.2 FR-6) — "登录成功后用户的主部门与最近一次有效同步结果一致"对登录与同步并发场景不清晰；当登录回调早于同步任务完成时主部门来源是缓存、上次同步还是钉钉本次返回？*Fix:* 写明读取顺序（如：登录时优先以钉钉返回 + 本地映射规则计算主部门；若同步进行中则使用上一次成功同步快照）。
- **high** FR-19 告警重试策略空 (§4.5 FR-19 / §11 风险表"告警噪声"行) — "成功、失败、重试状态可查询"未规定重试次数、间隔、最终失败的处理。FR-18 与 §11"默认低频"并未给出阈值数。*Fix:* 给出 V1 默认重试次数（如 3 次指数退避），最终失败必须可在后台一键重发并标记。
- **medium** FR-5 错误"可区分"未给可观测形态 (§4.2 FR-5) — 测试人员无法仅凭描述判断是否达标。*Fix:* 列出 V1 至少返回的 4 类错误码或后台标识。
- **medium** FR-15 CSV "一致" 口径未定 (§4.4 FR-15) — 排序、空值、未归属部门的 CSV 行如何呈现未定，导出与看板差一行就是 acceptance 失败。*Fix:* 明确"按当前筛选条件聚合后逐行输出，包含未归属部门行"；给一份示例字段顺序。
- **medium** FR-12 默认阈值缺省 (§4.3 FR-12) — "接近耗尽默认阈值在产品设置中明确"——但 PRD 内并未给。*Fix:* 给 V1 默认值（如 80% / 95% 两档）或转 OQ。
- **medium** FR-20 风险率口径定义缺失 (§4.5 FR-20) — "在页面说明统计口径"是 UI 要求，PRD 自身缺少口径文字（按部门/时间窗，是否扣除被拦截请求等）。*Fix:* 在 FR-20 写明"风险率 = 当周期内该部门触发风险事件请求数 / 部门请求总数；被拦截请求计入分子分母"。
- **low** §8 NFR 性能项未给数据量/响应时间阈值 (§8 NFR 性能) — 仅"不得逐条扫描全量日志"。*Fix:* 给一个上限假设（如"100 万条 log 下 30 天看板查询 < 3 s"），明确假设可由架构阶段调整。

## Scope honesty — strong

§5 非目标列表是真在工作：逐条点名 SaaS、LDAP/SAML/SCIM、飞书/企微登录、License、专用审计表、Group 替换。每一条都是简报或常识中容易"被默认会有"的项，把它们写成非目标避免下游 silent assumption。§6.2 MVP 范围外重申"本地组织管理 UI 仅作为开放问题"、"多部门用量分摊用主部门"、"上游开源贡献节奏不设 PRD 指标"——后者尤其诚实，承认了某些活动不应进入 SM。

§14 假设索引覆盖了三条 ASSUMPTION（V1 单企业自部署 / `tenant_id` 预留默认值 / 报告优先邮件），并在正文回链对应 §。OQ 集中在 §13，索引完整。

唯一的弱点是 OQ 密度（7 条）+ ASSUMPTION（3 条）共 10 条 open items，对一个绿灯 PRD 偏高，但每一条都是真问题，不是装饰。可接受。

### Findings

- **low** OQ 密度对绿灯 PRD 偏高 (§13) — 7 条 OQ 中 OQ-1（产品名）和 OQ-5（OAuth provider 选择）可在架构阶段处理；OQ-2 / OQ-3 / OQ-4 / OQ-6 / OQ-7 都直接影响 FR 验收。*Fix:* 进入 epic/story 前由 PM 至少关掉 OQ-6 / OQ-7 / OQ-4，把 OQ-2 / OQ-3 显式标为"架构阶段决策，不阻塞 V1 起步"。

## Downstream usability — strong

PRD 与 addendum 联动是这份文档最强项之一。术语表（§3）覆盖 12 条核心名词，"`Group`" / "部门" / "主部门" / "组织同步" 各自有清晰边界，FR / UJ / SM 全文未见混淆。FR 编号 FR-1..FR-20 连续无缺，UJ-1..UJ-4 / SM-1..SM-5 / SM-C1..SM-C3 / OQ-1..OQ-7 全连续，cross-reference 全部用 ID 而非"见上文"。每个 FR 都明确写"实现 UJ-X"，反向 UJ → FR 的关系也覆盖（UJ-1 与 FR-5/6/7/8 对应；UJ-2 与 FR-9/10/12 对应；UJ-3 与 FR-13/14/15 对应；UJ-4 与 FR-17/18/19 对应；FR-20 同时引用 UJ-3 与 UJ-4，恰当）。每个 UJ 有命名主角（林工 / 王经理 / 陈总 / 赵安全），并在主角段写明角色场景。术语表里 "`Group`" 的定义直接说明"V1 不把它替换为部门"，构成 FR-3 的术语级护栏。

## Shape fit — strong

定位为"棕地企业自部署 + 多管理员侧 stakeholder + 中等规模 V1 + 链头（喂 UX、架构、story）"，所采用的 shape 与定位一致：

- 多个管理员侧角色（林工 / 王经理 / 陈总 / 赵安全）→ UJ 是 load-bearing 的，PRD 给了四条带命名主角与边界情况的 UJ，配置正确。
- 棕地 → §10 集成与依赖、§9 约束与护栏、addendum §2 棕地现状摘要全部覆盖；并明确"不替换 Group / 不重写计费表达式 / 不删除 new-api / QuantumNous 标识"。
- 链头 → 下游可用性高（见上一节），addendum §3 列出 7 项架构待决策项喂给架构阶段，§4 给出建议表/模块方向但显式标注"非最终设计"。
- 没有过度形式化（4 个 UJ 不是 8 个），也没有欠形式化（不是无 UJ 的纯能力清单）。

唯一可斟酌：作为单企业自部署产品，consumer-product 风格的"价值时刻"段落对每条 UJ 都写了，对 IT 内部场景略显丰富但不至于成为 theater——四条价值时刻都直接绑回 acceptance（如 UJ-1"看到同步成功、失败、跳过和冲突记录"映射 FR-7 可验证结果），可接受。
