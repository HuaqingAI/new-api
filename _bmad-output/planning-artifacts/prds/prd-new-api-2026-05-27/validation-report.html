Decision-readiness

adequate

PRD 在多处把决策"做了"而不是"模糊掉"——FR-3 直接禁止把部门命名为 group，FR-11 明确部门只消费结算 quota，§5 非目标列表逐条点名 SaaS / LDAP / DeepWiki / 飞书企微 / License / 专用审计表，§9 把"不为 SaaS 公网注册牺牲 V1 交付"写成护栏。这些都是真决策。

但有两个真正的张力被推到 OQ：OQ-3（tenant_id 预留到新表 vs 旧表）是 V1 / V3 的取舍点，addendum A-2 已说明"扩旧表显著增加迁移、查询和索引改造成本"，但 PRD 主体只在 FR-4 写下"假设只在新增表预留"，没有让决策者看到"如果选扩旧表，V1 工期 / 复杂度的代价是什么"。OQ-2（无钉钉企业的本地组织 UI）通过 §11 风险表点出"6-8 周目标失控"做了反对面，但"6-8 周"从未在 PRD 主体出现。OQ-6（部门配额周期）和 OQ-7（多部门员工的主部门来源规则）会直接决定 FR-9 / FR-2 的可验收口径，应在故事拆分前关掉。

7 条 OQ + 3 条 ASSUMPTION 对一个被定位为"绿灯进入架构与 story"的 PRD 偏多；不至于 broken，但提示决策密度不足。

high

OQ-3 没有让取舍可比较

§13 OQ-3 / §4.1 FR-4 / addendum A-2
OQ 只问"是否扩到旧表"，PRD 主体没有把两条路径在 V1 工期、迁移成本、索引改造、SaaS 切换难度上的代价摆出来。决策者读完仍要回到 addendum 才能判断。
Fix: 在 §4.1 FR-4 或 §13 OQ-3 下增补两行表格："只新表预留：V1 +X 张表 schema，SaaS 切换需补 Y。扩到旧表：迁移影响 users/logs/quota_data，索引改造 Z 项。"让决策可读。

OQ-6 / OQ-7 决定 FR 验收口径却被推迟

§13 OQ-6, OQ-7 / §4.3 FR-9 / §4.1 FR-2
FR-9"周期配额"未定义周期是自然月还是自定义，FR-2"主部门"未定义来自钉钉主部门字段还是首次同步。两个问题都进入 V1 故事拆分前必须解决，否则 acceptance 写不实。
Fix: 在进入 epic/story 之前由 PM 与 IT 林工对齐两条规则，回填到 FR-9 和 FR-2 的"可验证结果"。
low

"6-8 周交付窗口"未在 PRD 内出现

§11 风险表 / §6 MVP
风险表第 6 行写"6-8 周目标失控"暗示有窗口约束，但 PRD 主体未声明 V1 时间盒。读者只能从 brief 推断。
Fix: §6 MVP 或 §12 发布与验收增一句"V1 目标交付窗口约 X 周（来自 brief）"。

Substance over theater

strong

四个 UJ 都不是装饰：UJ-1 林工带出"无可靠匹配标识进入待处理"，UJ-2 王经理带出"多部门员工只走主部门"，UJ-3 陈总带出"历史日志缺部门快照应显示未归属而非反推"，UJ-4 赵安全带出"通知失败不阻断事件落库"——四条边界情况都直接转化为对应 FR 的"可验证结果"或非目标项。愿景段第二段（§1）专门点出"中国中型企业 + 钉钉为优先入口"，与"通用企业 AI 治理"区分开。NFR（§8）八条都给了具体动作，不是"系统必须可扩展"式 NFR theater。SM 段配套 SM-C1..SM-C3 反向指标，对治理类产品尤其重要："错误绑定比未绑定更危险"、"配额拦截是治理能力，不是业务价值"、"告警必须可追溯避免噪声"——三条 counter-metric 写得到位。

Strategic coherence

strong

PRD 有清晰的赌注（§1 第二段："中国中型企业引入 AI 的首要阻力不是有没有模型入口，而是企业 IT 能否知道谁在用、哪个部门在花钱"），五大 FR 子节（4.1 组织模型 / 4.2 钉钉 / 4.3 部门配额 / 4.4 看板 / 4.5 内容监控）都直接服务这个赌注。FR-3 / FR-11 / 护栏 §9 共同守"不替换现有 Group 与计费表达式语义"这条主轴。SM-1（部门同步连续 14 天）、SM-2（30 天无超额漏算）、SM-3（5 分钟定位）覆盖三大主能力，且都不是 DAU/MAU 式活动量指标——SM-2 直接验证"额度可信"这一治理价值。MVP 范围（§6）与非目标（§5）边界一致，没有把 V2 / V3 内容漏进 V1。

Done-ness clarity

thin

这是 PRD 最该被 unforgiving 的维度，也是最薄的一项。结构上每条 FR 都有"可验证结果"小节，但若干条仍藏在形容词里：FR-5 错误"可区分"未规定错误码；FR-10 并发安全只写"不能超扣或漏扣"无量化；FR-6"登录成功后主部门一致"对登录与同步并发不清晰；FR-12 接近耗尽阈值 punted 到"产品设置"未给默认；FR-15 CSV"一致"未规定排序/空值；FR-19 重试策略未定；FR-20 风险率口径未给。NFR §8 性能项"看板默认时间范围查询不得依赖逐条扫描全量日志"是好边界，但没给响应时间或数据量阈值。

critical

FR-10 部门配额并发安全无可执行验证命题

§4.3 FR-10
addendum A-4 已说"FR-10 验收风险最高，应优先出技术设计和并发测试"，但 FR-10 仅写"不能造成超扣或漏扣"。这是 PRD 的核心治理承诺，下游 story 据此写不出 acceptance。
Fix: 增加"在 ≥N 并发、跨同部门 M 个用户、含 tiered_expr 模型的混合负载下，连续 X 分钟无部门剩余额度负数、无用户 quota 与部门 quota 终态偏差超过 ε"之类量化条件；并明确预消费 vs 结算两条路径上的扣减时机（addendum A-4 已枚举候选）。
high

FR-6 主部门一致性时机未定

§4.2 FR-6
"登录成功后用户的主部门与最近一次有效同步结果一致"对登录与同步并发场景不清晰；当登录回调早于同步任务完成时主部门来源是缓存、上次同步还是钉钉本次返回？
Fix: 写明读取顺序（如：登录时优先以钉钉返回 + 本地映射规则计算主部门；若同步进行中则使用上一次成功同步快照）。
high

FR-19 告警重试策略空

§4.5 FR-19 / §11 风险表"告警噪声"行
"成功、失败、重试状态可查询"未规定重试次数、间隔、最终失败的处理。FR-18 与 §11"默认低频"并未给出阈值数。
Fix: 给出 V1 默认重试次数（如 3 次指数退避），最终失败必须可在后台一键重发并标记。
medium

FR-5 错误"可区分"未给可观测形态

§4.2 FR-5
测试人员无法仅凭描述判断是否达标。
Fix: 列出 V1 至少返回的 4 类错误码或后台标识。
medium

FR-15 CSV"一致"口径未定

§4.4 FR-15
排序、空值、未归属部门的 CSV 行如何呈现未定，导出与看板差一行就是 acceptance 失败。
Fix: 明确"按当前筛选条件聚合后逐行输出，包含未归属部门行"；给一份示例字段顺序。
medium

FR-12 默认阈值缺省

§4.3 FR-12
"接近耗尽默认阈值在产品设置中明确"——但 PRD 内并未给。

FR-20 风险率口径定义缺失

§4.5 FR-20
"在页面说明统计口径"是 UI 要求，PRD 自身缺少口径文字（按部门/时间窗，是否扣除被拦截请求等）。

Scope honesty

strong

§5 非目标列表是真在工作：逐条点名 SaaS、LDAP/SAML/SCIM、飞书/企微登录、License、专用审计表、Group 替换。§6.2 MVP 范围外重申"本地组织管理 UI 仅作为开放问题"、"多部门用量分摊用主部门"、"上游开源贡献节奏不设 PRD 指标"——后者尤其诚实，承认了某些活动不应进入 SM。§14 假设索引覆盖了三条 ASSUMPTION，并在正文回链对应 §。OQ 集中在 §13，索引完整。唯一的弱点是 OQ 密度（7 条）+ ASSUMPTION（3 条）共 10 条 open items 对绿灯 PRD 偏高，但每一条都是真问题，可接受。

Shape fit

strong

定位为"棕地企业自部署 + 多管理员侧 stakeholder + 中等规模 V1 + 链头（喂 UX、架构、story）"，所采用的 shape 与定位一致。多个管理员侧角色 → UJ 是 load-bearing 的，PRD 给了四条带命名主角与边界情况的 UJ。棕地 → §10 集成与依赖、§9 约束与护栏、addendum §2 棕地现状摘要全部覆盖；并明确"不替换 Group / 不重写计费表达式 / 不删除 new-api / QuantumNous 标识"。链头 → 下游可用性高，addendum §3 列出 7 项架构待决策项喂给架构阶段，§4 给出建议表/模块方向但显式标注"非最终设计"。没有过度形式化（4 个 UJ 不是 8 个），也没有欠形式化。
